# 后端工程规范

> 跨栈规则不在此重复，见 `../cross-cutting/`：
> 安全与鉴权、并发与幂等、面向失败的设计、API 契约与 DTO、测试与校验、变更管理（Git / 依赖 / ADR）。

## 1. 适用范围

本规范适用于 NestJS 后端项目。

## 2. 后端边界

Controller 控制器不应当存放大量业务逻辑。
业务规则应当放在后端 Service 服务层、领域层、应用层，遵循项目既有架构。

后端拥有最终决定权：

- 业务规则
- 权限鉴权
- 数据完整性
- 状态流转

## 3. 架构

依赖流向优先遵循：
HTTP 请求 → 控制器 → 应用层 / 服务层 → 领域业务逻辑 → 持久化层
若现有仓库架构存在刻意差异化设计，则遵从原有架构。

## 4. 控制器

控制器主要职责：

- HTTP 请求入参接收
- DTO 数据绑定校验
- 认证上下文处理
- 权限校验边界拦截
- 接口响应数据封装映射

**禁止在控制器中编写大量业务逻辑**。

## 5. 服务层

服务层负责：

- 业务流程编排
- 业务规则实现
- 事务边界管控
- 对接协调外部依赖服务

## 6. 业务不变约束

业务强制校验规则**必须在服务端实现**。
示例场景：

- 资源归属权限校验
- 多租户数据隔离
- 合法状态流转校验
- 操作唯一性约束
- 库存数量限制

## 7. 异常处理

禁止对外暴露以下信息：

- SQL 原始报错
- 程序堆栈信息
- 密钥、敏感凭证
- 内部基础设施细节

使用业务层统一、稳定的错误码 / 错误语义对外返回。

## 8. 外部服务调用

对接每一个外部依赖服务，都需要考虑：

- 请求超时时间
- 重试机制
- 重试次数上限
- 服务失败降级行为
- 可观测性（日志 / 监控）
- 幂等性保障

永远不要假设外部服务永远可用。

## 9. 数据库事务

当多个数据库操作需要保证业务约束一致性时，使用事务。
需要权衡：

- 事务执行时长
- 锁持有时间
- 事务隔离级别
- 锁竞争风险
- 事务内产生的外部副作用

不要无意义地长时间持有事务。

## 10. 查询性能

代码评审需要关注：

- N+1 查询问题
- 返回结果无上限的查询
- 缺失必要索引
- 返回数据集过大
- 多余联表 Join
- 分页逻辑
- 排序逻辑

## 11. 日志打印

日志需要便于问题排查，记录内容包含：

- 执行的业务操作
- 请求相关上下文
- 用户 / 租户上下文（适用场景下）
- 耗时延迟
- 依赖服务异常
- 失败根本原因

严禁打印密钥、凭证等敏感信息到日志。

## 12. 后端完成定义（DoD，完成准入检查项）

提交前需要评审核对：

- DTO 参数校验
- 接口权限鉴权
- 业务不变约束校验
- 并发安全处理
- 幂等性设计
- 事务边界是否合理
- 异常错误处理
- 数据库性能影响
- Redis 使用影响
- 外部依赖异常行为处理
- 项目构建打包

> 
> 术语备注
> 
> 
> - DTO：Data Transfer Object 数据传输对象
> - Prisma：NodeJS ORM 数据库框架
> - DoD：Definition of Done，研发 “完成” 的验收标准
> - Idempotency：幂等性，多次执行效果和一次执行一致
> - Business Invariants：业务不变约束，业务必须永远成立的规则
