# MFA 多因素认证 · 小白入门指南

> 本文面向第一次接触 MFA 的同学，结合本仓库 `admin-api` 的真实实现，
> 讲清楚「MFA 是什么、为什么需要、在这个项目里是怎么跑起来的」。
>
> 对应代码：`apps/admin-api/src/modules/mfa/`（MFA 自助管理）、
> `apps/admin-api/src/modules/auth/`（登录二步验证）。
> 设计依据：ADR-013 D8。

---

## 1. 什么是 MFA？

MFA = **Multi-Factor Authentication**，中文叫「多因素认证」。

一句话：**登录时除了密码，还要再验一个别的东西。**

| 因素类型         | 例子                 | 特点                                 |
| ---------------- | -------------------- | ------------------------------------ |
| 你知道的（知识） | 密码、PIN 码         | 可能被偷：钓鱼网站、撞库、键盘记录器 |
| 你拥有的（物品） | 手机上的动态码、U 盾 | 小偷远程拿不到                       |
| 你本身的（生物） | 指纹、人脸           | 需要专用设备，后台系统一般不用       |

生活中最常见的例子：进小区要**门禁卡 + 指纹**，两道都过了才能进。
只偷到卡（密码）没用，还要有你的手指（手机动态码）。

**为什么光有密码不够？** 密码会泄露：你在钓鱼网站输过一次、别的网站拖库后你复用了同一个密码、电脑中了木马……密码一旦泄露，账号就等于裸奔。
而动态验证码 30 秒变一次，且只存在于你自己的手机上——偷走了密码也过不了第二关。

---

## 2. 本项目的 MFA 方案：TOTP 动态验证码

### 2.1 TOTP 是什么

TOTP = **Time-based One-Time Password**（基于时间的一次性密码）。

原理可以想象成「**两个人对着同一块表，用同一本密码本，各自算出同一个答案**」：

```text
         ┌─────────────── 共享密钥 secret ───────────────┐
         │                                               │
         ▼                                               ▼
  ┌─────────────┐                                ┌─────────────┐
  │  你的手机    │                                │   服务器     │
  │ 认证器 App   │   密钥 + 当前时间(每30秒一格)    │  (admin-api) │
  │             │  ───────────────────────────►  │             │
  │ 显示: 834 152│     双方独立计算，结果相同        │  期望: 834152 │
  └─────────────┘                                └─────────────┘
```

- 绑定时，服务器把一个随机生成的 **secret（密钥）** 交给你的认证器 App（扫码）。
- 之后双方用「secret + 当前时间」各自算 6 位数字，**每 30 秒换一个**。
- 登录时你说出 App 上显示的数字，服务器算一遍比对——对上了，证明「你手机里有这个 secret」，也就是证明你是本人。

**好处**：不需要联网、不需要发短信（省短信费，也不怕 SIM 卡被劫持）、断网也能登录。
常用 App：Google Authenticator、Microsoft Authenticator、1Password 等，扫码即用。

### 2.2 恢复码（Recovery Codes）

**手机丢了 / 换手机了，App 没了怎么办？**

绑定 MFA 时，服务器一次性生成 **10 个恢复码**（8 位十六进制大写，如 `A3F9C2D1`）。
每个恢复码：

- **只能用一次**，用一次少一个（服务端记录使用时间）；
- 效力等同 TOTP 验证码，登录二步验证时输恢复码也能通过；
- **只在绑定时明文显示这一次**，服务端只存 SHA-256 摘要（见 §6），忘了就找不回来。

所以绑定时的正确姿势：**把这 10 个码抄到纸上/存到密码管理器里，别只截图在手机里**——手机丢了截图也跟着没了。

## 3. 核心名词速查表

| 名词                     | 是什么                                                                                  | 在哪出现                     |
| ------------------------ | --------------------------------------------------------------------------------------- | ---------------------------- |
| `secret`                 | TOTP 共享密钥，base32 字符串                                                            | 绑定时返回一次，之后加密存库 |
| `otpauth URI`            | 形如 `otpauth://totp/FedStack:用户名?secret=...` 的链接，前端把它画成二维码             | 绑定时返回                   |
| `pendingToken`           | 「待验令牌」：密码对了但还差一步 MFA 时发的临时 JWT                                     | 登录第一步的响应             |
| 策略 `security.mfa.mode` | 租户/平台级配置：`DISABLED` / `OPTIONAL` / `REQUIRED`                                   | 数据库 SysConfig 表          |
| `enabledAt`              | MFA 完成绑定的时间；为 null 表示「绑定中」（还没验证首码，可重新 setup 或免验证码取消） | `sys_user_mfa` 表            |

## 4. 流程一：绑定 MFA（首次设置）

绑定发生在**已登录**之后（用户中心/安全设置里操作），共 4 步：

```text
 前端                        后端 (MfaService)                 认证器 App
  │                              │                              │
  │ ① POST /mfa/setup            │                              │
  │─────────────────────────────►│ 生成 secret + 10 个恢复码     │
  │                              │ secret 加密落库(enabledAt=null│
  │                              │ = 绑定中)，恢复码只存摘要      │
  │◄───── otpauth URI ───────────│                              │
  │◄───── secret 明文 ───────────│                              │
  │◄───── 恢复码明文(仅此一次)────│                              │
  │                              │                              │
  │ ② 把 otpauth URI 画成二维码 ─────────────扫码─────────────► │
  │                              │              App 保存 secret │
  │                              │                              │
  │ ③ 用户看 App 上的 6 位数字                                    │
  │    POST /mfa/bind { code }   │                              │
  │─────────────────────────────►│ 解密 secret → 验证 code      │
  │                              │ 通过 → enabledAt = now()     │
  │◄──────────── 绑定完成 ────────│                              │
```

逐条说明：

1. **`POST /mfa/setup`**：服务器生成 20 字节随机 secret 和 10 个恢复码，先写库（状态=绑定中）。如果用户已有**已启用**的 MFA 记录，返回 409「已绑定，如需重置请先解绑」；如果已有的只是「绑定中」记录（`enabledAt = null`），则**重新生成并原子覆盖** secret 与恢复码（见下方注意事项）。恢复码明文**只在这一个响应里出现一次**。
2. **扫码**：前端把 `otpauthUri` 渲染成二维码（后端不生成二维码图片），用户用认证器 App 扫码保存；扫不了可手动输入 `secret`。
   - `secret` 和 `otpauthUri` 里带的密钥是**同一个东西**（base32 明文），只是两种投递形式：URI 给二维码扫，`secret` 给「没摄像头 / 用桌面版认证器 / 二维码画不出来」时手工填写。前端只需二选一呈现，不是两套密钥。
   - 它就是这套 MFA 的**主密钥**：拿到它的人可以永久算出有效验证码。所以只能在绑定环节明文出现，前端不得写日志/埋点，传输必须走 HTTPS。
3. **`POST /mfa/bind { code: "6位数字" }`**：用户把 App 当前显示的数字提交回来。服务器解密库里的 secret，算一遍比对。**这一步是故意的**——证明用户真的扫码成功了，而不是随手点过就算绑上。
4. 验证通过 → 写入 `enabledAt`，绑定生效。

> 注意：只调了 `setup` 但一直不调 `bind` 的用户处于「绑定中」状态（`enabledAt = null`），登录时**不会**被要求二步验证（只有 `enabledAt ≠ null` 才算启用）。这条记录也不构成死锁：`setup` 可以重新生成覆盖它，`unbind` 也可以免验证码取消它。

## 5. 流程二：登录二步验证（最重要的流程）

### 5.1 两种登录的对比

**没启用 MFA 的用户**（一路绿灯）：

```text
 POST /auth/login(账号+密码)
   → 密码校验通过
   → 直接签发 access/refresh 令牌，登录完成
```

**启用了 MFA 的用户**（多一道门）：

```text
 前端                              后端 (AuthService)              认证器 App
  │                                   │
  │ ① POST /auth/login               │
  │    { username, password, ... }    │
  │──────────────────────────────────►│ 租户校验 → 锁定判定 → 验证码
  │                                   │ → 密码校验……全部通过
  │                                   │ 检查：策略≠DISABLED 且用户已启用 MFA？
  │                                   │ 是 → 不发正式令牌！
  │                                   │ 签发 pendingToken(5分钟,一次性)
  │◄── { mfaRequired: true,           │
  │      pendingToken,                │
  │      expiresIn: 300 } ────────────│
  │                                   │
  │ ② 前端看到 mfaRequired=true       │
  │    弹出「请输入动态验证码」        │
  │                                   │
  │ ③ 用户看 App: 834 152             │
  │    POST /auth/mfa/verify          │
  │    { pendingToken, code: "834152"}│
  │──────────────────────────────────►│ 七道校验(见 5.3)
  │                                   │ 通过 → 建 Redis 会话
  │                                   │ 签发正式 access/refresh 令牌
  │◄── { accessToken, ... }           │
  │    (refresh 写入 HttpOnly Cookie) │
```

关键点：**密码通过 ≠ 登录成功**。启用 MFA 的用户在第二步验证完成前，拿不到任何正式令牌，访问不了任何受保护的接口。

### 5.2 `pendingToken`（待验令牌）的设计

为什么密码对了不发正式令牌，而要发一个中间态令牌？

- **它证明「密码这关已过」**：第二步接口不需要再传账号密码，凭它就知道验证的是哪个人；
- **短有效期**：300 秒（5 分钟），超时就得从头登录；
- **一次性**：每个 pendingToken 有唯一 `jti`，在 Redis 存了标记。**验证通过时才 `DEL` 消费**——之后再用同一个 token 提交会被拒绝（**防重放**：万一 token 被截获，攻击者也用不了第二次）；输错验证码不会消耗它（见 5.4）；
- **类型隔离**：JWT 里的 `typ = 'mfa-pending'`，与 access/refresh 令牌不同类型。拿 pendingToken 去调业务接口？门都没有——它过不了正常鉴权；反过来拿 access token 冒充 pendingToken 也不行（类型校验会拦）。

### 5.3 第二步的七道校验（顺序即安全）

`POST /auth/mfa/verify` 收到请求后，按固定顺序做七件事：

| 顺序 | 校验                                                                      | 防的是什么                                                  |
| ---- | ------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 1    | JWT 签名 + 有效期                                                         | 伪造的 / 过期的 pendingToken                                |
| 2    | `typ === 'mfa-pending'`                                                   | 拿 access/refresh 令牌冒充待验令牌                          |
| 3    | 账号维度 MFA 锁定判定（10 次失败/30 分钟窗口）                            | 攻击者反复登录刷新的 pendingToken，绕过单次挑战的计数       |
| 4    | pending 存活检查（Redis `GET`，只读不消费）                               | 已过期/已消费的挑战；同时避免在死挑战上白白烧掉恢复码       |
| 5    | 验证码本身：6 位 → 走 TOTP 比对；否则按恢复码比对（用过的恢复码直接拒绝） | 没有手机/恢复码的攻击者                                     |
| 6    | 用户状态复核（还在、未删除、ACTIVE）                                      | 「等待输入验证码的 5 分钟里，账号被管理员禁用了」这种时间差 |
| 7    | 消费 `jti`（Redis `DEL`，仅验证通过后执行）                               | 同一 token 重放/并发提交两次：仅先到者消费成功              |

全部通过才建会话、发正式令牌。任何一步失败，得到的都是笼统的「用户名或密码错误」类错误——**不告诉攻击者具体哪步错了**。

### 5.4 验证码输错了怎么办？

- **可以原地重试**：输错不会消耗 pendingToken。同一个挑战内最多错 **5 次**（`MFA_VERIFY_LIMITS.challengeMaxAttempts`），第 5 次失败后挑战作废，需重新走密码登录拿新的 pendingToken；
- **账号维度另有累计**：跨挑战累计错 **10 次**（30 分钟窗口）会临时锁定 MFA 验证，锁定期内连正确的验证码也拒，并向本人发站内信安全提醒（`MFA_VERIFY_LIMITS.accountMaxAttempts / accountWindowMinutes`）；验证通过一次即清零；
- TOTP 有 **±30 秒时钟容差**（`window: 1`，RFC 6238 建议），手机时间略不准也能过；
- 恢复码：输错没关系，只有**输对**才会消耗掉那一个；
- 所有失败都会写登录日志（`MFA_INVALID` / `MFA_LOCKED`），可聚合统计与告警。

> 演进说明：早期实现是「先消费 jti 再验码」（输错一次即需重新登录），后按 NIST SP 800-63B / OWASP 建议改为「验证通过后再消费 + 双维度失败计数」，详见 §13。

## 6. 流程三：解绑与重置恢复码

| 操作       | 接口                             | 需要提供                                               | 说明                                               |
| ---------- | -------------------------------- | ------------------------------------------------------ | -------------------------------------------------- |
| 解绑       | `POST /mfa/unbind`               | 已启用：TOTP 6 位码 **或** 恢复码 8 位；绑定中：可省略 | 整条 MFA 记录删除                                  |
| 重置恢复码 | `POST /mfa/recovery-codes/reset` | 仅 TOTP 6 位码                                         | 旧的 10 个全部作废，发新的 10 个（同样只显示一次） |

设计意图：

- **解绑必须验证**，防止别人借你电脑顺手把 MFA 关了；
- 解绑接受**恢复码**——手机丢了时这是你自救的通道；
- **「绑定中」记录免验证码取消**——它尚未生效、不参与登录判定；用户刷新页面后可能既没扫码也没保存恢复码，必须留一个自助出口；
- 重置恢复码**只认 TOTP**（有手机才能重置），防止攻击者拿偷到的一个恢复码反复「重置」出新的恢复码。

另外有 `GET /mfa/status` 查询当前状态：是否绑定、是否启用、恢复码还剩几个——前端可以据此提醒「恢复码只剩 2 个了，建议重置」。

## 7. 策略开关：DISABLED / OPTIONAL / REQUIRED

存在 SysConfig 表，键为 `security.mfa.mode`，**租户级配置优先，没有则回落平台级**（遮蔽语义，同 ADR-009）。都没配时默认 `OPTIONAL`。

| 模式               | 登录时的行为                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| `DISABLED`         | 完全忽略 MFA，即使绑了也不要求二步验证                                                         |
| `OPTIONAL`（默认） | **绑定了且启用** MFA 的用户必须二步验证；没绑的正常登录                                        |
| `REQUIRED`         | 与 OPTIONAL 在当前登录链路行为一致；语义上表示「要求启用」，但为向后兼容不阻断未绑定的存量用户 |

两点容易误解的地方：

- 策略**只影响登录链路**要不要二步验证，**不影响**用户自助绑定/解绑——策略是 DISABLED 时，用户依然可以绑定（预留了 `DISABLED_BY_POLICY` 错误码，当前代码暂未启用）；
- 绑定/解绑是纯自助端点，**只需要登录态，不需要按钮级权限码**。

## 8. 安全设计细节（面试官最爱问的「为什么」）

| 设计                | 做法                                                                                                 | 为什么                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| secret 加密存储     | AES-256-GCM 加密后存 `secret_cipher` 字段，格式 `iv:tag:密文`，密钥来自环境变量 `MFA_SECRET_ENC_KEY` | 数据库被拖库时，攻击者拿到的只是密文；GCM 还能检测密文是否被篡改。密钥不进数据库，与应用配置隔离 |
| 恢复码只存摘要      | 库里存 `{ hash: SHA-256(码), usedAt }`，明文只返回一次                                               | 同密码哈希一个道理：拖库也还原不出可用恢复码；`usedAt` 保证一码一用                              |
| pendingToken 一次性 | Redis key 存在性即「未使用」，**验证通过后才 `DEL`**，删除成功=消费                                  | JWT 本身签发后无法作废，靠 Redis 补上「只能用一次」；通过后消费兼顾重试体验                      |
| 半成品令牌隔离      | `typ: 'mfa-pending'` 独立类型                                                                        | 防止「差一步」的令牌被当正式令牌用，也防伪造                                                     |
| 用户状态复核        | 二步验证最后重查用户是否 ACTIVE/未删除                                                               | 封堵 5 分钟窗口期的时间差漏洞                                                                    |
| 错误信息笼统        | 二步失败统一报凭据错误                                                                               | 不给攻击者逐步试错的路标                                                                         |
| 接口限流            | `/auth/login`、`/auth/mfa/verify` 都挂了限流                                                         | 防暴力枚举 6 位验证码                                                                            |
| 二维码前端渲染      | 后端只返回 `otpauth URI` 文本                                                                        | 后端不引入二维码依赖，职责分离                                                                   |

## 9. API 一览

MFA 自助管理（需要登录态，走 `/api` 前缀，Bearer access token）：

| 方法 | 路径                        | 作用                                                       |
| ---- | --------------------------- | ---------------------------------------------------------- |
| GET  | `/mfa/status`               | 查询状态（是否绑定/启用、恢复码剩余数）                    |
| POST | `/mfa/setup`                | 发起绑定：返回 otpauth URI、secret、恢复码（明文仅此一次） |
| POST | `/mfa/bind`                 | 提交 6 位首码，完成绑定                                    |
| POST | `/mfa/unbind`               | 解绑（已启用需 TOTP 或恢复码；绑定中免验证码）             |
| POST | `/mfa/recovery-codes/reset` | 重置恢复码（需 TOTP）                                      |

登录链路（公开端点，有限流）：

| 方法 | 路径               | 作用                                                                           |
| ---- | ------------------ | ------------------------------------------------------------------------------ |
| POST | `/auth/login`      | 第一步：密码验证。启用 MFA 时返回 `{ mfaRequired, pendingToken }` 而非正式令牌 |
| POST | `/auth/mfa/verify` | 第二步：提交 `{ pendingToken, code }`，通过后返回正式令牌                      |

### 9.1 前端视角：什么时候触发哪个接口

所有触发点都来自**用户动作**或**上一个接口的响应**，没有任何一个是「进页面就自动打」的：

| 触发时机                                  | 调什么                           | 关键说明                                                    |
| ----------------------------------------- | -------------------------------- | ----------------------------------------------------------- |
| 登录页点「登录」                          | `POST /auth/login`               | 前端**不需要**提前知道用户有没有 MFA                        |
| 登录响应里 `mfaRequired === true`         | 不发请求，切到验证码步骤         | 分支由**响应驱动**，不要先查 `/mfa/status` 去猜             |
| 用户在验证码框点「确认」                  | `POST /auth/mfa/verify`          | 带上响应里的 `pendingToken` 和用户输入的 6 位码             |
| 进入「安全设置」页                        | `GET /mfa/status`                | 只读接口，可随时调，用来渲染开关与恢复码剩余数              |
| 点「开启 MFA」按钮                        | `POST /mfa/setup`                | **写操作**，必须用户点击才调，绝不能在 `onMounted` 里自动跑 |
| `status` 返回 `bound=true, enabled=false` | 视界面选择其一                   | 「绑定中」三个出口：继续绑定 / 重新生成二维码 / 取消绑定    |
| 绑定中点「继续绑定」                      | `POST /mfa/bind`                 | 已扫码的用户输 6 位首码即可，不依赖当初的 setup 响应        |
| 绑定中点「重新生成二维码」                | `POST /mfa/setup`                | 覆盖绑定中记录，旧的 secret 与恢复码立即失效                |
| 绑定中点「取消」                          | `POST /mfa/unbind`               | 空 body，免验证码                                           |
| 二维码页点「下一步 / 完成绑定」           | `POST /mfa/bind`                 | 提交用户输入的 6 位首码                                     |
| 点「关闭 MFA」并在弹窗输入验证码          | `POST /mfa/unbind`               | 6 位 TOTP 或 8 位恢复码均可                                 |
| 点「重置恢复码」并在弹窗输入 TOTP         | `POST /mfa/recovery-codes/reset` | 只接受 6 位 TOTP，不接受恢复码                              |

登录侧的伪代码就是一次「两段式」：

```ts
const res = await api.post('/auth/login', { tenantCode, username, password });
if ('mfaRequired' in res) {
  // 不跳首页，进入第二步；pendingToken 存内存（或 sessionStorage，见下）
  mfaState.pendingToken = res.pendingToken;
  router.push('/login/mfa');
  return;
}
// 正常登录完成：accessToken 在响应体，refresh 已由后端写入 HttpOnly Cookie
router.push('/');
```

### 9.2 前端必须守住的四条纪律

1. **`setup` 只能在用户点击时调用**。它会在库里创建一条「绑定中」记录（`enabledAt = null`），调了又不用就会留下垃圾状态。
2. **`setup` 的响应只显示一次，丢了就找不回**。`secret` / 恢复码明文只在这一次响应里，后端没有「再查一次密钥」的接口。所以二维码页要做：
   - 「我已保存恢复码」确认（下载 / 复制 / 勾选）后才允许进入下一步；
   - 监听 `beforeunload` 拦截刷新与关闭（只能拦截，不能保证——手机切后台、崩溃、强制关闭都绕过它）；
   - 绑定完成前刷新了页面也不至于卡死：已扫码的用户凭 `POST /mfa/bind` 继续完成；没扫码的用户按 `GET /mfa/status` 的 `bound=true, enabled=false` 走 `POST /mfa/setup` 重新生成二维码（覆盖绑定中记录），或走 `POST /mfa/unbind`（空 body）取消。`secret` / 恢复码**不要持久化到 localStorage / sessionStorage**——重开绑定即可，别把主密钥暴露给 XSS。
3. **`pendingToken` 的存放位置**：优先放内存（Pinia / Zustand），刷新即丢、回登录页重来最安全；若要抗刷新可放 `sessionStorage`（同标签页有效、关标签即清）；**不要放 localStorage**（长期驻留，等于把「差一步的登录态」存盘）。
4. **错误要分流处理**，别一律弹「操作失败」：

   | 现象                                                | 前端动作                                                                        |
   | --------------------------------------------------- | ------------------------------------------------------------------------------- |
   | `/auth/mfa/verify` 报「令牌无效 / 已使用 / 已过期」 | 清掉 `pendingToken`，回登录页并提示重新登录                                     |
   | `/auth/mfa/verify` 凭据类错误（验证码错）           | **原地重试**，不清 `pendingToken`（同一挑战可错 5 次，超限才会被作废，见 §5.4） |
   | `POST /mfa/setup` 返回 409                          | 说明记录已启用（绑定中会被直接重新生成）；重新拉 `/mfa/status` 刷新界面         |
   | `POST /mfa/bind` 返回 400 TOTP 错误                 | 不要重新 `setup`，等 App 下一个 30 秒窗口重试                                   |
   | `POST /mfa/bind` 返回 409「绑定状态已变更」         | 记录被其他标签页重新生成或删除；重新拉 status，仍绑定中则重新扫码后再提交       |
   | `POST /mfa/unbind` 返回 400「请提供验证码」         | 已启用的 MFA 必须带 TOTP/恢复码；绑定中记录直接空 body 提交即可                 |
   | 任意登录/验证接口返回 429                           | 提示「尝试过于频繁，请稍后再试」，不要自动重试                                  |

此外两个体验点：`GET /mfa/status` 返回的 `recoveryCodesRemaining <= 2` 时建议在设置页挂一条提醒；`enabled === false && bound === true` 表示用户停在「绑定中」，UI 应给出「继续完成绑定 / 重新生成二维码 / 取消绑定」三个出口。

## 10. 错误码一览

MFA 模块业务错误码（模块号 97，见 `modules/mfa/errors.ts`）：

| 场景                         | HTTP | 含义                                                                       |
| ---------------------------- | ---- | -------------------------------------------------------------------------- |
| `MFA 未绑定`                 | 404  | 对未绑定的用户执行 bind/unbind 等操作                                      |
| `MFA 已绑定`                 | 409  | 对已启用记录重复 setup（绑定中记录会被覆盖）；或取消绑定时发现已被并发启用 |
| `TOTP 验证码错误`            | 400  | bind / unbind / reset 时动态码不对                                         |
| `恢复码无效或已使用`         | 400  | 恢复码不存在或已被消耗                                                     |
| `当前 MFA 策略为 DISABLED`   | 403  | 预留错误码，当前代码暂未启用                                               |
| `绑定状态已变更`             | 409  | 提交首码期间 secret 被重新生成或记录被删除，需重新扫码                     |
| `请提供 TOTP 验证码或恢复码` | 400  | 解绑已启用的 MFA 未带 code                                                 |

登录二步失败（`/auth/mfa/verify` 中 pendingToken 无效/过期/已消费、验证码错误）统一归入认证错误，**不细分原因**。唯一例外是账号维度 MFA 锁定（30 分钟内错满 10 次）：返回 `10A03`（429，「账号已锁定，请 30 分钟后重试」），便于前端明确提示锁定时长。

## 11. 数据库里存了什么

表 `sys_user_mfa`（模型 `SysUserMfa`，一个用户一条记录，`user_id` 唯一）：

| 字段                    | 内容                                                            |
| ----------------------- | --------------------------------------------------------------- |
| `user_id` / `tenant_id` | 属主用户与租户（雪花 ID）                                       |
| `secret_cipher`         | AES-256-GCM 加密后的 TOTP secret（VarText 500）                 |
| `recovery_codes`        | JSON 数组：`[{ hash: "sha256摘要", usedAt: "使用时间或null" }]` |
| `enabled_at`            | 绑定完成时间；null = 绑定中（未验证首码）                       |

会话与一次性标记在 **Redis**：正式会话由 SessionService 管理；pendingToken 的 `jti` 标记（key `AUTH_MFA_PENDING(jti)`，TTL 300 秒）用于一次性消费。MFA 失败计数也在 Redis：挑战维度 `AUTH_MFA_CHALLENGE_FAIL(jti)`（TTL 与 pending 相同，上限 5 次）、账号维度 `AUTH_MFA_ACCOUNT_FAIL(tenantId, username)`（30 分钟窗口，上限 10 次），由 `MfaAttemptService` 管理，验证通过即清零账号计数。

## 12. 常见问题（FAQ）

**Q1：30 秒要过去了，我输到一半怎么办？**
等 App 上数字刷新后，用新的数字重新提交即可。输错**不会**消费 pendingToken：同一个挑战内最多错 5 次，第 5 次失败后挑战才作废、需要回登录页重新输密码；另外跨挑战累计错 10 次（30 分钟窗口）会临时锁定 MFA 验证（见 §5.4）。TOTP 本身有 ±30 秒容差，边界时刻提交的相邻窗口验证码也能通过。

**Q2：手机丢了，怎么登录？**
用绑定时保存的**恢复码**走 `POST /auth/mfa/verify`（8 位那个）。10 个恢复码每个只能用一次。登进去后赶紧解绑重绑，或重置恢复码。

**Q3：恢复码用完了怎么办？**
登录后用 TOTP 验证码调 `POST /mfa/recovery-codes/reset` 重新生成 10 个。

**Q4：换新手机了怎么办？**
认证器 App 数据不会自动跟过去。新手机上要么从旧 App 导出/迁移账号，要么用恢复码登录后解绑重绑。

**Q5：为什么绑定要「setup → 扫码 → bind」三步，不能一步到位？**
bind 那一步是在**验证你真的扫上了**。如果只 setup 就算绑定，App 没扫成功，用户就被锁在门外了。

**Q6：绑定了 MFA 就一定会被要求二步验证吗？**
不一定。登录时同时看两个条件：租户策略 ≠ `DISABLED` **且** 你的 MFA 已启用（`enabledAt` 非空）。「只 setup 没验证首码」「策略是 DISABLED」都不会触发二步验证。

**Q7：MFA_SECRET_ENC_KEY 没配置会怎样？**
服务启动时打警告日志，MFA 功能不可用（加密密钥为空）。所以部署时必须配好这个环境变量。

**Q8：pendingToken 泄露了会怎样？**
攻击者还得同时拿到你的动态码，且要赶在 5 分钟内、在验证通过被消费之前用掉；同一挑战错 5 次即作废，账号维度错 10 次（30 分钟）直接锁定。这是「短 TTL + 一次性 + 类型隔离 + 双维度计数 + 限流」多层防护共同兜底的结果。

## 13. 企业级一般怎么设计二步验证（参考与差距）

先给结论：**主流企业级产品几乎都不是「输错一次就作废」，而是「有限重试 + 分层防线」**。本项目早期实现是「先消费 jti 再验码」的保守取舍，**现已按本节路径完成演进**：当前实现为「验证通过后才消费 + 双维度失败计数 + TOTP 容差 + 审计通知」，即下方 13.4 的 5 步已全部落地。

### 13.1 标准与依据

- **NIST SP 800-63B**（美国数字身份标准）：验证方**应当**做失败限速，但明确允许用户在锁定前进行**多次**连续尝试（上限放宽到 100 次）。标准本身就假定「一次挑战内可以输错重试」。
- **RFC 6238**（TOTP 协议标准）：明确建议验证方接受 **±1 个时间步**（即前后各 30 秒）的容差窗口，因为手机时钟漂移很常见。本项目已采纳（`TOTP_WINDOW = 1`）。
- **OWASP MFA Cheat Sheet**：推荐「失败计数 + 渐进延迟 + 锁定 + 告警」组合，而非单次作废。

### 13.2 企业级典型分层防线

没有任何一层是万能的，企业级靠**叠加**：

```text
   攻击者拿到密码
        │
        ▼
 ┌─────────────────────────┐ 第 1 层：挑战态本身
 │ pendingToken / challenge │  TTL 5~10 分钟、绑定会话上下文、
 │  TTL + 类型隔离 + 服务端态 │  服务端存状态（不只靠 JWT 签名）
 └─────────────────────────┘
        │
        ▼
 ┌─────────────────────────┐ 第 2 层：单次挑战内的尝试计数
 │  每个 challenge 3~5 次    │  超限作废、强制重新登录
 │  失败计数（Redis INCR）   │  ← 这是「重试」与「防枚举」的平衡点
 └─────────────────────────┘
        │
        ▼
 ┌─────────────────────────┐ 第 3 层：账号维度失败计数
 │  跨 challenge 累计失败    │  防攻击者反复登录刷 challenge
 │  N 次锁定 M 分钟 + 通知   │  绕过第 2 层（本项目已有 LoginAttemptService 先例）
 └─────────────────────────┘
        │
        ▼
 ┌─────────────────────────┐ 第 4 层：IP 维度限流
 │  Throttler（本项目已有）   │  挡洪泛；NAT/企业代理下不能单独依赖
 └─────────────────────────┘
        │
        ▼
 ┌─────────────────────────┐ 第 5 层：审计与告警
 │  MFA 失败事件落审计日志    │  连续失败主动通知用户本人
 └─────────────────────────┘
```

### 13.3 与本项目逐项对比

| 维度                       | 本项目当前实现                                        | 企业级常见做法                   |
| -------------------------- | ----------------------------------------------------- | -------------------------------- |
| 单次挑战可重试次数         | **5 次**（超限作废挑战，需重新登录）✅ 已落地         | 3~5 次，超限才作废               |
| 挑战 TTL                   | 5 分钟                                                | 5~10 分钟（相当）                |
| 挑战一次性                 | 验证**通过后**才消费 jti ✅ 已落地                    | 验证**通过后**再消费             |
| TOTP 时钟容差              | ±1 窗口（±30 秒，`TOTP_WINDOW = 1`）✅ 已落地         | ±1 窗口（±30 秒，RFC 6238 建议） |
| 账号维度 MFA 失败锁定      | 10 次/30 分钟，锁定拒验 + 站内信通知 ✅ 已落地        | 有，且常伴随用户通知             |
| IP 限流                    | 5 次/分钟（已有）                                     | 有（相当）                       |
| MFA 失败审计/告警          | `MFA_INVALID` / `MFA_LOCKED` 登录日志 + 锁定站内信 ✅ | 有审计 + 连续失败告警            |
| Remember this device       | 无                                                    | 企业 SSO 常见（30 天免二步）     |
| 风险自适应（新设备才触发） | 无（策略仅三态全局开关）                              | 企业 IdP（Okta/Entra ID）常见    |

### 13.4 演进路径（已全部落地 ✅）

以下 5 步原为企业级演进建议，**当前代码已全部实现**：

1. ✅ **改消费顺序**：`verifyMfa` 中 `cache.del(jti)` 在验证码校验**通过之后**执行；
2. ✅ **加挑战内失败计数**：`AUTH_MFA_CHALLENGE_FAIL(jti)` 用 Redis `INCR`，上限 5 次，超限 `DEL` 掉 `jti`（强制重新登录）；
3. ✅ **TOTP 开 ±1 窗口**：`totp.validate({ token, window: 1 })`（`TOTP_WINDOW = 1`），消化手机时钟漂移；
4. ✅ **账号维度计数**：新增 `MfaAttemptService`（复用 `LoginAttemptService` 模式），10 次/30 分钟窗口，超限锁定 MFA 验证并拒绝后续尝试；
5. ✅ **MFA 失败写审计日志 + 连续失败通知**：失败写 `MFA_INVALID` / `MFA_LOCKED` 登录日志；账号维度锁定时通过 `MessageCenterService.sendDirect` 向本人发站内信安全提醒。

后续可选方向（未实施）：Remember this device（30 天免二步）、风险自适应触发（新设备/异地才要求 MFA）。
